# Device invitations

## Purpose and trust boundary

An organisation administrator creates a short-lived, single-use activation
code for a new iOS or Android installation. The employee enters that code in
the native app's activation screen. This is an authenticated management API;
it is deliberately separate from the public deployment-registry exchange.

```text
administrator -- authenticated management API --> create invitation
                                                   |
                                                   v
employee -- one-time code --> fixed registry exchange --> deployment_id
```

The management API derives the target tenant and deployment from the
authenticated administrator. A client must never submit a `tenant_id`,
`deployment_id`, API URL, or signing key when it creates an invitation.

The code is an activation credential only. It is not a user token, API key, or
tenant authorisation grant. Normal login and API requests remain responsible
for user authentication, tenant authorisation, issuer, audience, and scopes.

## Transport and authentication

All paths below are relative to the existing authenticated management API base:

```text
/deployment-enrollment-codes
```

- iOS and Android send the ordinary authenticated `Authorization: Bearer`
  session header to the native management API base selected by the verified
  deployment profile.
- Flutter Web uses the existing **same-origin BFF** route. It authenticates
  through the BFF's HttpOnly session cookie and CSRF protection; it must not
  send a cross-origin bearer token or receive an arbitrary upstream URL.
- The backend/BFF must enforce the same administrator permission for both
  transports. Hiding the Flutter screen is not authorisation.

Responses are JSON with `Content-Type: application/json` and
`Cache-Control: no-store`, except the empty successful `DELETE` response.
Requests and responses must not be redirected.

## API contract

### Create an invitation

```http
POST /deployment-enrollment-codes
Accept: application/json
Content-Type: application/json
Cache-Control: no-store

{"expires_in_minutes":30}
```

The request body is exactly one member:

| Member | Type and rule |
| --- | --- |
| `expires_in_minutes` | JSON integer from `1` through `1440`, inclusive. |

On success, return `200 OK` with exactly:

```json
{
  "id": "00000000-0000-4000-8000-000000000001",
  "enrollment_code": "OPAQUE_ONE_TIME_CODE",
  "expires_at": "2026-08-21T12:30:00Z"
}
```

`id` is a canonical lowercase RFC 4122 UUID. `enrollment_code` is a non-empty
opaque ASCII code generated by the server. `expires_at` is a canonical RFC
3339 UTC timestamp ending in `Z` (for example, `2026-08-21T12:30:00Z`). The
raw code is returned **only** by this response so the
administrator can copy it or send it through an approved channel.

### List invitations

```http
GET /deployment-enrollment-codes
Accept: application/json
Cache-Control: no-store
```

Return `200 OK` with exactly:

```json
{
  "items": [
    {
      "id": "00000000-0000-4000-8000-000000000001",
      "expires_at": "2026-08-21T12:30:00Z",
      "status": "active"
    }
  ]
}
```

Each item has exactly `id`, `expires_at`, and `status`. `status` is one of
`active`, `redeemed`, `expired`, or `revoked`. The list response **never**
contains `enrollment_code`, its hash, or another recoverable form of the code.

### Revoke an invitation

```http
DELETE /deployment-enrollment-codes/{id}
Cache-Control: no-store
```

`id` is the canonical invitation UUID from the create or list response. A
successful revocation returns `204 No Content` with an empty body. The endpoint
must be idempotent for an invitation that is already revoked; it must never
reveal or reissue the raw code.

## Backend requirements

1. Require an authenticated administrator with an explicit permission to
   manage deployment invitations. Scope every operation to the tenant and
   deployment derived from that principal; do not trust client-supplied scope.
2. Generate codes with a cryptographically secure random generator. Store only
   a suitable salted/peppered verifier or hash, not the raw code. Do not log
   raw codes in application, proxy, analytics, audit, crash, or support logs.
3. Enforce the requested expiry server-side, with a maximum of 1,440 minutes.
   Return a UTC `expires_at` value and treat expiry as authoritative even if a
   device clock is incorrect.
4. Redeem a code atomically in the registry exchange. A conditional database
   update/transaction must guarantee that only one successful redemption can
   return a deployment ID. Expired, revoked, or previously redeemed codes must
   fail without leaking deployment details.
5. Support administrative revocation immediately. Record an audit event for
   issuance, redemption, expiry, and revocation using the invitation ID or a
   non-sensitive code fingerprint only.
6. Rate-limit creation, listing, revocation, and especially registry
   redemption. Apply appropriate per-principal, tenant, source, and code
   verifier limits. Return typed, non-sensitive errors such as `forbidden`,
   `invalid_expiry`, `not_found`, `rate_limited`, and `unavailable`.
7. Do not expose the raw enrollment code after creation, include it in a URL,
   or turn it into a permanent company credential. A QR code, if added later,
   is only a delivery format for the same one-time code.

## Relationship to the fixed registry

The API in this document creates and administers codes. It does **not** replace
the native public exchange:

```text
POST {DEPLOYMENT_REGISTRY_URL}/v1/enrollments/exchange
{"enrollment_code":"ONE_TIME_CODE"}
```

That fixed-registry endpoint remains unauthenticated, accepts only the
one-time code, atomically consumes it, and returns only `deployment_id`. The
native app then obtains and verifies the signed deployment profile before it
uses any tenant or API root. See [Deployment registry](DEPLOYMENT_REGISTRY.md)
for the exchange and signed-profile contract.
